**Skill body requirements (implement ALL of the following, in this order):**

---

**Section 1 — Derived-view framing (D-07, CAPT-07) — MUST be the first paragraph:**

State explicitly that `wiki/inbox/_session.md` is a derived view of what currently exists in the codebase. The codebase is ground truth. If Claude finds an inbox entry that contradicts what the user just asked it to do, the inbox is wrong — update it, do not push back on the user. Example wording (exact wording at executor's discretion, but these concepts must appear):

> The inbox at `wiki/inbox/_session.md` is a derived view of what exists in the codebase right now. The codebase is ground truth. If you ever find an inbox entry that contradicts what the user just asked you to do — for example, an entry for a function the user just asked you to delete — the inbox is wrong. Update it. Do not push back on the user citing inbox state.

---

**Section 2 — Entry format (D-06, CAPT-03):**

Every entry is a handle line followed by a body:

```
@ CATEGORY::slug  •  path-or-em-dash  •  #tag1 #tag2
One-to-three sentences describing the artifact in its current state.
```

Rules:
- CATEGORY is one of: `ARCHITECTURE`, `FUNCTIONS`, `RESEARCH`, `SELF`, `DIAGRAMS` (from `wiki/Rules.md §2`)
- slug is kebab-case (matches the concept name)
- path is the primary source file path, or `—` for non-file artifacts (decisions, session notes)
- #tags are lowercase, 2–5 tags
- The handle line MUST start at column 0 (no leading whitespace) — required for `^@ ` grep-prune
- Body is factual present-tense description of what currently exists, not what happened ("Added X" → wrong; "X does Y" → correct)

Include one worked example showing an entry for a function:
```
@ FUNCTIONS::compute-replacement-level  •  src/lib/vorp/replacement.ts  •  #function #vorp #math
Computes the replacement-level threshold for a given position by sorting eligible players descending
and taking the value at index = league_size * roster_slots[position]. Returns NaN if pool < slot count.
```

---

**Section 3 — No-op guard (D-09, CAPT-05) — check FIRST before any file I/O:**

Before reading the inbox or making any edits: build a scratch-list from this turn's tool calls. If the scratch-list is empty (the turn produced no Edit/Write/MultiEdit tool calls, no Bash commands that created or deleted files, and no explicit user request to record something), STOP. Write nothing. Return immediately. Do not re-read the inbox, do not run grep, do not write a "no changes" line. The turn was a no-op relative to the inbox.

This is load-bearing for per-turn cost (CAPT-05): the fast path costs zero file I/O.

---

**Section 4 — Scratch-list protocol (D-01, CAPT-06):**

From this turn's tool call history (Claude's fresh memory), enumerate every thing touched:
- Files **created**: new files written by Write/MultiEdit
- Files **modified**: files changed by Edit/Write/MultiEdit  
- Files **deleted**: files removed by Bash rm or explicit delete operations
- **Explicit user requests**: if the user asked "record X" or "note Y", include that too

This scratch-list IS the evidence base (CAPT-06): every inbox add or update must trace to an item on this list. Do not add entries for things not on the list.

---

**Section 5 — Reconcile loop (D-01, D-02, CAPT-04):**

For each item on the scratch-list:

**Deleted items (prune first):**
1. Run `grep -n "^@ [A-Z]*::<slug>" wiki/inbox/_session.md` where `<slug>` is the kebab-case slug matching the deleted artifact's name. Find the matching entry block (handle line + body lines until the next blank line or next `^@ ` line).
2. Remove the entire entry block using Edit.
3. If multiple entries reference the deleted artifact (e.g., a test file entry mentions the deleted function), update those entries to remove the reference.

**Created or modified items (add/update):**
1. Run `grep -n "^@ [A-Z]*::<slug>" wiki/inbox/_session.md` to check if an entry already exists.
2. If it exists: update the body paragraph to reflect the current state of the artifact. Do not append — replace the body.
3. If it does not exist: append a new entry at the end of the file (below the last existing entry, with a blank line separator).

**The 1+1-then-deleted worked example (inline in the skill body — REQUIRED, per D-01/D-02 design rationale and CAPT-04):**

> **Example — create then delete in the same session:**
>
> *Turn 1:* You wrote `add(a, b)` in `math.ts`. Your scratch-list has `math.ts` as created/modified. You check the inbox — no `FUNCTIONS::add` entry exists. You append:
> ```
> @ FUNCTIONS::add  •  math.ts  •  #function #math
> Adds two numbers. Returns a + b.
> ```
>
> *Turn 2:* The user asks you to remove `add`. You delete it from `math.ts`. Your scratch-list has `math.ts:add` (or equivalent) as deleted. You grep the inbox for `^@ FUNCTIONS::add ` (or `^@ [A-Z]*::add `), find the entry, and remove the entire block. After this turn, the inbox contains zero entries for `add`. A digest run at this point produces zero filed notes for `add`. **This is correct.**

---

**Section 6 — Full-sweep trigger (D-02, hybrid pruning):**

After the reconcile loop completes, check whether a full sweep is needed:

```
entry_count=$(grep -c "^@ " wiki/inbox/_session.md 2>/dev/null || echo 0)
```

Trigger a full sweep if EITHER:
- `entry_count` > 50, OR
- The user's most recent prompt invoked or mentioned `/digest` (pre-digest sweep)

**Full sweep protocol:**
For every entry in the inbox (not just the ones touched this turn):
1. Extract the `path` field from the handle line.
2. If path is `—` (non-file artifact like a decision or session note): keep the entry; these are not file-grounded.
3. If path is a file path: check whether the file still exists (use Read or Glob). If the file is gone and the entry's slug matches nothing currently in the codebase: remove the entry.
4. Report how many entries were pruned to the user in a single summary line: "Full sweep: pruned N stale entries."

The full sweep is O(N entries) but triggered only when entry count exceeds 50 or just before digest — so it runs rarely.

---

If `wiki/inbox/_session.md` does not exist when this skill fires, create it with the standard header (same content as Task 1 produces) before proceeding. This handles the bootstrapping case where a consuming repo installs the skill but has not yet initialized the inbox.
